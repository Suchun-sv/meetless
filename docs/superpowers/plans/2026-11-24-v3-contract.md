# Meetless v3: the shared contract for the Phase 1 blocks

This document is for the planners and implementers of the four Phase 1 blocks: **S** (server, MCP, accounts), **U1** (shell, dashboards, chat, setup, login, agents page), **U2** (needs board, drawer, handoff, link, confirm and conflicts) and **U3** (inputs, artifacts with OnlyOffice and capture, activity, deliveries). It states what exists on `v3` once Phase 0 (`docs/superpowers/plans/2026-11-24-v3-phase0-base.md`) is merged. That covers module paths, exported names and signatures, who owns which file, and how blocks stay out of each other's way.

The design (`docs/superpowers/specs/2026-11-24-meetless-v3-design.md`) and the prototype (`design/claude-design-v3/`) are the authority on behaviour. This contract is the authority on names. If you need a name that is not here, see §1 "Changing shared things".

### Changing shared things

`packages/core` is frozen. `packages/core/test/contract.test.ts` pins `EVENT_TYPES` and every runtime export. If your block really needs a core change, make it a separate commit that touches only `packages/core` (and its tests). The change must be additive (a new function or an optional field), and the commit message must start with `core:`. List it in your merge description. A changed signature or a new event type needs the base owner's sign-off before you build on it. Derived data your UI needs belongs in your own folder's `model.ts` (pure, tested). Do not put it in core.

## 2. Core (`@meetless/core`, `packages/core/src`)

The client's `live` state is already the signed-in user's own view, because the server filters each user's stream. Call the queries on `live` directly. Anything that leaves the user must be built from `shareableView(live)`: a link preview, a prompt copied for someone else, a delivery note.

### Frozen event types (44)

Payloads are in `events.ts`. Entries marked † are new in Phase 0; `project.renamed` came later (§12.23). Entries marked **svc** are service-only: a client command with that type is rejected. `work.recorded` with `via` set is also service-only.

New payloads:
- `work.linked { workId; needId; effect?: WorkEffect | null }`
- `work.ignored { workId }`
- `artifact.shared { artifactId; snapshot? }`. The server fills `snapshot`; clients send `{ artifactId }`. The same holds for `need.shared` and `input.shared`.
- `chat.asked { messageId; scope: 'home' | projectId; text; reply: AgentReply }`
- `chat.cleared { scope }`

`work.recorded` gains `autoLinked?: boolean`.

### State additions

- `State.chats: Record<string, ChatThread>`, keyed `dashboardKey(userId, scope)`.
- `ChatThread { userId; scope; messages: ChatMessage[]; clearedSeq }`
- `ChatMessage { id; text; reply: AgentReply; at; seq }`
- `WorkItem.ignored` and `WorkItem.autoLinked`
- `Need.autoRound`, which drives the drawer's 「规则识别 改」 mark on the round (`ai.rules`, 12.10).

### Rules worth knowing

- Need context version is `needVersion(n) = 1 + revisions`.
- Only the sender confirms or reopens a handoff.
- A conflict is decided by its `deciderId`, or by the target need's owner while the conflict is open.
- Progress is `isProgress(w) = !w.capture && !w.ignored`. Agent reports over MCP count as progress. Captures never do.
- Private needs are coded `Np1` / `Hp1` and get a shared code when shared.

## 3. Shared API contract (`@meetless/api`, `packages/api/src`)

The package is renderer-safe, with no Node imports. Files: `routes.ts`, `types.ts`, `mcp.ts`, `errors.ts`, re-exported from `index.ts`.

```ts
type ApiName = keyof ApiSpec;
interface RouteDef { method: 'GET' | 'POST' | 'DELETE'; path: string; auth: 'user' | 'agent' | 'none'; from: readonly ('app' | 'mcp')[] }
const API_ROUTES: { [K in ApiName]: RouteDef };
type ApiRequest<K extends ApiName> = ApiSpec[K]['req'];   // path params are fields of req
type ApiResponse<K extends ApiName> = ApiSpec[K]['res'];
type AppApiName = /* union of the ApiName keys whose route has from including 'app' and auth !== 'none' */;
const APP_ROUTE_NAMES: readonly AppApiName[];

interface ApiErrorBody { error: { code: string; details?: unknown } }   // every non-2xx response
const API_ERROR_CODES = ['UNAUTHENTICATED','INVITE_INVALID','INVITE_USED','TOKEN_REVOKED','NOT_IMPLEMENTED','NOT_AVAILABLE','EXTRACT_FAILED','TOO_LARGE','RATE_LIMITED'] as const;   // RATE_LIMITED: 429, details { retryAfter } (12.8)
const CLIENT_HEADER = 'x-meetless-client';                // 'claude-code' | 'codex' | other label
```

Semantics S must keep:
- Every read goes through `service.view(userId)`, so private items of others never appear.
- `context.get` records `handoff.context_fetched` only when the caller uses an **agent** token and is the recipient of an open handoff on that need. A personal-token call (an app preview) never records one.
- `work.record` sets `via { client: <x-meetless-client or token label>, tokenId }`. The work counts as progress.
- `needs.propose` appends `proposal.created`, which lands in 「待确认」.
- `inputs.import` extracts text (md and txt as given, docx and pdf on the server), runs `toParagraphs` and `detectExtracts` over the importer's visible needs, shared needs only when `private: false` (`detector: 'rules/1'`; core refuses a shared input whose `rev` extract names a private need, 12.22), and appends `input.imported` as the user.
- The DocumentServer fetches the file from a signed, short-lived URL: `GET /v1/office-files/:ticket`. It takes no bearer token, is not in `API_ROUTES`, and is served only on the Unix socket `MEETLESS_OFFICE_FILES_SOCKET` (12.6).

**MCP** (`mcp.ts`):

```ts
const MCP_TOOLS = ['get_need_context','list_needs','search','read_artifact','record_work','propose_need','set_verdict'] as const;
type McpToolName = (typeof MCP_TOOLS)[number];
const MCP_WRITE_TOOLS: ReadonlySet<McpToolName>;          // record_work, propose_need, set_verdict
const MCP_TOOL_ROUTE = { get_need_context: 'context.get', list_needs: 'needs.list', search: 'search', read_artifact: 'artifacts.read',
  record_work: 'work.record', propose_need: 'needs.propose', set_verdict: 'needs.verdict' } as const;
type NeedRef = { link: string } | { projectId: Id; code: string };
interface McpToolSpec {
  get_need_context: { in: NeedRef & { locale?: 'zh-CN' | 'en' }; out: ApiResponse<'context.get'> };
  list_needs: { in: { projectId: Id } & ApiRequest<'needs.list'>; out: ApiResponse<'needs.list'> };
  search: { in: ApiRequest<'search'>; out: ApiResponse<'search'> };
  read_artifact: { in: ApiRequest<'artifacts.read'>; out: ArtifactRead };
  record_work: { in: NeedRef & { text: string; why?: string; effect?: WorkEffect; date?: IsoDate }; out: ApiResponse<'work.record'> };
  propose_need: { in: { projectId: Id } & Omit<ApiRequest<'needs.propose'>, 'projectId'>; out: ApiResponse<'needs.propose'> };
  set_verdict: { in: NeedRef & { status: 'testing' | 'held' | 'refuted' | 'parked'; verdict: string }; out: ApiResponse<'needs.verdict'> };
}
const MCP_PATH = '/mcp' as const;
```

MCP is served by the Meetless server itself, not a per-machine stdio package: route `POST /mcp`, Streamable HTTP via the official MCP TypeScript SDK's server transport, running in the server process, stateless. Auth is `Authorization: Bearer <agent token>`, with the same agent-token rules as `API_ROUTES` (records `via`, fetched versions, privacy scope). The calling client's label comes from the `x-meetless-client` header (`CLIENT_HEADER`), else the token's own label. `/mcp` is not an `API_ROUTES` entry.

i18n already has the label `t.<tool>` for every tool, and a test checks it.

## 4. Bridge (`@meetless/client/bridge`, `packages/client/src/bridge.ts`)

The bridge is the renderer's only path to the network and the disk. Every method returns a result object and never throws. `Result<T> = ({ ok: true } & T) | { ok: false; code: string; details?: unknown }`.

### Design tokens and base classes (`styles/`)

**Rule:** UI blocks reference only these variables and classes. Never write a raw colour (hex, `rgb()`, `hsl()`, `oklch()` or a named colour), font family, shadow or radius value in CSS or in a `style` prop. Inline styles carry geometry only. If you need a token that is missing, ask base; do not invent one locally. `apps/desktop/test/styles.test.ts` enforces this: it fails on raw values outside `tokens.css`, on `var(--x)` names that are not defined, and on violet used outside AI and rule styles. It applies the same rules to every stylesheet, block files included:
- **Colour:** no hex, `rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color()` or named colour; `transparent` and `currentColor` are allowed. `color-mix(in <space>, var(--a) N%, var(--b))` is allowed only with token arguments.
- **Font, shadow, radius:** `font-family` is `var(--font-sans)`, `var(--font-mono)` or `inherit`; the `font` shorthand only `inherit`. `box-shadow` is `none` or `var(--shadow-*)`; no `text-shadow`. Every `border-*-radius` is a `--radius-*` token or `0`.
- **Type scale:** `font-size` and `font-weight` are tokens; `line-height` is a token or `1`; `letter-spacing` is a token or `0`.
- **Spacing scale:** `padding*`, `margin*`, `gap`, `row-gap` and `column-gap` take `--space-*` tokens, `0`, `auto`, `%`, `vh` or `vw`. A value between steps is a `calc()` of tokens and unitless numbers, for example `calc(var(--space-1) / 2)` or `calc(var(--space-1) * -1)`.
- **Border widths:** `border*`, `outline` and `outline-offset` carry no raw `px`; use `var(--border)`, `var(--border-strong)` or `var(--border-width)`, for example `var(--border-width) dashed var(--color-border-strong)` or `calc(var(--border-width) * 2)`. Widths, heights and positions are layout and may be `px`.
- **No dots:**
  - no circular radius on `::before`, `::after` or `::marker`;
  - no pseudo-element of 10px or less in both width and height with a background, because that is a square marker;
  - no `clip-path`, `shape-outside` or `mask` of `circle()` or `ellipse()`;
  - no dot, bullet, square or circle characters in stylesheets or in renderer `.ts`/`.tsx` sources;
  - no `dotted` lines;
  - `list-style` is only `none`;
  - no `.km*` classes;
  - progress bars use `--radius-sm`, and their fill has a minimum width.
  - the one allowed small shape is the timeline milestone diamond `.tl-ms` (the approved v4 milestone); no other element of 10px or less in both dimensions may be filled, bordered, shadowed or outlined (R73).
- **`--radius-full` allowlist:** only selectors whose last compound has one of the classes `.av`, `.pill`, `.nav-n`, `.count`, `.lock` and `.capl` (avatars, pills, count badges, tags). A new round element is requested from base and added here.
- **Violet:** `--color-ai` and `--color-ai-bg` appear only where some compound selector carries one of these exact class sets. Classes are matched whole, so `.hotel` or `.fixed` do not pass.
  - `.tone-ai`
  - `.chip.hot`, `.sugg.hot`; `.hot` alone is not enough
  - `.card-ai.ask`
  - `.w-agent`
  - `.thread-h`
  - `.para.hit`, `.oo-b.hit`; a selected paragraph is violet only as `.hit.on`, and a plain `.on` is neutral
  - `.oo-tag`
  - `.fix`
  - `.srow.asking`

  Only the subject compound and its descendant or child ancestors count; a `+` or `~` sibling does not. Classes inside `:not()`, `:is()`, `:where()` or `:has()` never count. Handoffs to you (`.hoff.hot`, `.hob.hot`) use the info tone.
- **Hover shadows:** a `:hover` `box-shadow` sits under the motion media query below.
- **Custom properties and fonts:** no custom property is declared outside `tokens.css`; `@font-face` lives only in `styles/fonts.css`, with relative URLs.
- **Motion:** `translate` and `scale` transforms (and any other transform) only under `@media (hover: hover) and (pointer: fine) and (prefers-reduced-motion: no-preference)`.
  Exceptions outside that query, and no others (R73; `styles.test.ts` `STATIC_TRANSFORMS` holds exactly these): `transform: translateX(-50%)` on any selector, for positioning (centring), not motion (the `translate` property is not an exception); `transform: rotate(45deg)` only on `.ms-hard` and `.ms-cadence`, which draws the timeline milestone diamond `.tl-ms`; and `transform: rotate(90deg)` only on `.refuted[open] summary::before`, the disclosure state, which reduced motion snaps without a transition. None of them on a `:hover`, `:active` or `:focus` state.
- **Style props:** `style` props in `.tsx` are object literals whose keys are all in `GEOMETRY_STYLE_KEYS` (`test/support/markup.ts`): `left`, `top`, `right`, `bottom`, `inset`, `width`, `height`, `minWidth`, `maxWidth`, `minHeight`, `maxHeight`, `flexBasis`, `gridColumn`, `gridRow`, `gap` and `transform` (a literal of translate and scale only); any other key, a spread or a computed key fails.

**Values.** The values are in `docs/superpowers/specs/2026-11-24-meetless-v3-visual-tokens.md`, approved by the user on 2026-11-24 (warm monochrome, flat cards, 1px light borders, crisp radii, near-zero shadows, following the `minimalist-ui` skill). Changing a value touches only `tokens.css`. Fonts are bundled offline: `styles/fonts.css` (imported before `tokens.css`) declares Geist, Geist Mono and Noto Sans SC from `assets/fonts/`, with no CDN. `color-mix(in srgb, var(--a) N%, var(--b))` is allowed when every colour argument is a token. These stay fixed whatever the values: the ChatGPT-like layout (grey sidebar, white canvas, drawer on the right, composer at the bottom), a monochrome base, violet only for AI and rule output, and no dot symbols.

### 12.8 Rate limiting (R46, R49, R51)

- `RATE_LIMITED` is the last entry of `API_ERROR_CODES`. Its HTTP status is 429, and its body is `{ error: { code: 'RATE_LIMITED', details: { retryAfter: <seconds> } } }`.
- **S builds** the limits. Only failures are counted and limited; the key is the client IP:
  - sign-in: 10 failed sign-ins per 5 minutes. A failed sign-in is a request whose bearer token fails authentication (`UNAUTHENTICATED` or `TOKEN_REVOKED`).
  - `invites.redeem`: 10 failed redemptions per 10 minutes.
  - A request with a valid token always passes, even from a limited IP (a shared NAT must not lock everyone out). A request with no token does not count.
  - Over the limit, the failing request answers 429 `RATE_LIMITED` with `details: { retryAfter: seconds }`.
- UI: show `t('error.RATE_LIMITED', { seconds: retryAfter })`: 「尝试太频繁，请 {seconds} 秒后再试。」 / "Too many attempts. Try again in {seconds}s.". `errorText(code)` takes no params, so call `t` directly.
- Client as built (R49): `callApi` (so every `api(...)`), `signIn` and `redeemInvite` map any non-2xx body `{ error: { code, details } }` to `{ ok: false, code, details }`. `HTTP_<status>` is used only when the body has no code; a bare 401 on `signIn` gives `UNAUTHENTICATED`. So `RATE_LIMITED` carries `details.retryAfter` on all three. `signIn` adds `details.url`; `redeemInvite` adds `details.url` and also keeps the server's details under `details.cause`.
- `setup/SignIn.tsx` exports `signInError(app, r, server)`. For `RATE_LIMITED` it shows `t('error.RATE_LIMITED', { seconds: Math.ceil(details.retryAfter) })`; without a numeric `retryAfter` it shows `error.generic` with the code, never a made-up wait.

### 12.9 Privacy rules added in Phase 0 (R42, R43, R37, R60)

- Core: `need.shared` throws `PRIVATE_SOURCE` while `source.inputId`, or the `inputId` of any `revisions[]` entry, names an input that is still private.
  - U2's 「公开到项目」 on such a need offers `common.shareSourceFirst` 「先公开来源输入」 / "Share the source input first". It is one click: `input.shared { inputId }` for each such input, then `need.shared { needId }`.
  - `error.PRIVATE_SOURCE` is generic: 「来源输入仅你可见，请先公开到项目。」 / "The source input is only visible to you. Share it with the project first."
- Core, `need.created` (`checkSource` in `packages/core/src/reducer.ts`, Task 11, R60): a `source.inputId` that is missing, belongs to another project or is not visible to the author gets `NOT_FOUND`, one answer for all three, so ids cannot be probed. A shared need that cites a private input, even the author's own, gets `PRIVATE_SOURCE`, as `need.shared` does.
- Server: `submit` and `appendTrusted` refuse `input.imported` or `artifact.version_added` when the actor neither uploaded nor can read (`canReadBlob`) its `blobHash`. The refusal is `NOT_AUTHORISED` with `details { what: 'blob', id: <hash> }`. Upload the blob as the same actor first. `appendSystem` is exempt.
- Core, inputs (final fix wave, C1): a shared input never names a private need. `input.imported` without `private: true` gets `PRIVATE_ITEM` when a `rev` extract targets a private need; `input.shared` gets `PRIVATE_ITEM` while an undecided `rev` extract targets a still-private need (share the need first, or decide the extract while the input is private). `extract.accepted` gives its work item `need.privateTo ?? input.privateTo`. `error.PRIVATE_ITEM` (「这一项仅你可见，先公开到项目。」 / "This item is only visible to you. Share it with the project first.") is the message for both. The `input.shared` refusal carries `details: { needIds }`, the private needs its undecided `rev` extracts target.
- Known limitation (R37): shared work may carry ids of private items (`alsoNeedId`, `source.inputId`). No content is reachable from them through blobs, context, search or MCP. **S builds** a regression test: another user resolving such an id gets `NOT_FOUND`.

### 12.23 Project rename

A project can be renamed after it is created. This is one new event type, so `FROZEN_EVENT_TYPES` in `packages/core/test/contract.test.ts` has 44 entries; no runtime export was added.

- `project.renamed { projectId; name }`. Any project member may send it, the same rule as `project.member_added` (`requireMember`): anyone else gets `NOT_A_MEMBER`, and an unknown project gets `NOT_FOUND`. The service has no separate check. `SyncService.submit` validates through core, as it does for every client command.
- Name rule: the reducer cleans the name with `noDots`, then trims it. An empty result, or a name longer than 80 characters, is `INVALID_EVENT` with details `{ field: 'name' }` (and `max: 80` when it is too long). Characters are counted as code points, so a CJK or astral character counts once. The stored name is the cleaned one; the payload keeps what the client sent.
- Scope: `open(projectId)`, like `project.created` and `project.member_added`. Every current member receives it.
- State: `Project.renames: ProjectRename[]`, oldest first, where `ProjectRename { from; to; by; at; seq }`. `from` is the name before and `to` the cleaned new name; `at` is the event's `recordedAt`. `project.created` starts it as `[]`. A rename to the same name is accepted and recorded; the UI does not send one.
- UI (renderer, base): the top-bar project name (`top-rename`) and each sidebar project row (`nav-project-rename`, with `data-project`) open an inline edit, `rename-input`. Enter saves, Esc cancels, and blur saves, like the hypothesis verdict field in `DrawerEdit`. An unchanged name sends nothing. The renderer checks the rule from `shell/rename.ts` `renameCommand` before it sends anything, and shows `pj.nameEmpty` / `pj.nameTooLong` as an error notice. A refusal from the service goes through the usual `submit` notice (`errorText(code)`).
- Activity: `stream/model.ts` `streamSystemRows` turns each rename into a system line (`stream-sys`, text `stream.renamed`), sorted with the work rows by date and then by seq. It shows only under the unfiltered view (kind `all`, no need picked), since a rename belongs to no kind and no need.
- i18n: `pj.rename` 「重命名」 / "Rename", `pj.nameEmpty`, `pj.nameTooLong` (U1 section) and `stream.renamed` (U3 section).
- e2e: `apps/desktop/e2e/ux-rename.spec.ts`. Alex renames a project from the top bar, and Zhou's client shows the new name live, in the sidebar row and as an Activity line.
