# Meetless v3 Phase 0 (Base) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn branch `v3` into a green base for parallel work. That means a completed and frozen v3 core, a shared API and MCP contract package, the server, client and desktop moved onto the new core, a routed renderer skeleton on a design-token layer with the prototype's layout, sample data, and per-block isolation. Four block agents can then build without guessing each other's interfaces.

**Architecture:** `packages/core` stays the single event-sourced domain. This phase adds what the design and prototype need and then freezes event types and exports with a test. The server keeps its append, read and push channel, but each stored event now carries its privacy scope (`project_id`, `private_to`), and every read filters by membership and privacy. The new `@meetless/api` package describes the HTTP routes and MCP tools as data and types. The client gets one generic `api()` bridge method. The renderer becomes a route table of placeholder pages in per-block folders, laid out like the prototype and styled only through named design tokens, whose values come from the design doc. The new `@meetless/sample` package turns the prototype's two projects into real commands.

**Tech Stack:** pnpm 12.23 monorepo, TypeScript 7 strict, vitest 5, Fastify 5 + ws, PostgreSQL 16 (`meetless-pg`), node:sqlite, Electron 45.4.1, Vite 8, React 19, Playwright 1.65.

**Spec:** `docs/superpowers/specs/2026-11-24-meetless-v3-design.md` (binding; in Chinese). The UI spec is `design/claude-design-v3/` (entry `Meetless Needs Prototype v3.html`). The names this plan produces are restated, for the block planners, in `docs/superpowers/plans/2026-11-24-v3-contract.md`. If the plan and the contract disagree, fix both in the same commit.

- All builds, tests and screenshots run on the dev server: `ssh -o BatchMode=yes <user>@<dev-server> 'bash -lc "cd ~/github/meetless && export PATH=$HOME/.local/bin:$HOME/bin:$PATH DOCKER_HOST=unix:///run/user/1000/docker.sock && <cmd>"'`. The login shell is fish, so always wrap commands in `bash -lc`. Below, only `<cmd>` is written.
- Do not touch the trial server: worktree `~/work/meetless-mac-pkg`, port 4875, schema `meetless_trial`, `~/work/meetless-trial`. Do not stop or reset `meetless-pg` or its volume. Also keep port 4876 and schema `meetless_trial_v3` free; they are reserved for the later v3 trial.
- Docker: use only `meetless-*` resources, bind them to 127.0.0.1 only, and check names and ports first. No prune, no sudo, no system packages. Start dependencies only with `bash infra/dev/deps.sh start`, which is an idempotent `up -d`. Never run `stop` or `reset`.
- Electron never opens a window on a desktop. It runs only through the Xvfb container (`infra/dev/electron-e2e.sh`).
- Git: commit messages carry no Co-authored-by or AI trailer. Never force-push. Never commit secrets.
- Text: zh-CN and en are fully covered and checked by the completeness test. Copy is short, like a commercial product.
- No dot symbols anywhere in the UI or its copy: no `·`, `•` or `●`, no asterisk bullets, no status dots. Facts are separated with spacing (core `SEP`, an em space). Core `DOT_RE` is the check.
- Visual values are not frozen. The renderer uses only the named tokens in contract §8 (colour, type, spacing, radius, border, shadow, layout, motion). Their values come from the design doc's design-tokens section, which follows the "taste" design skill. These stay fixed: the ChatGPT-like layout, a monochrome base, violet reserved for AI and rule output, and no dot symbols.
- AI is simulated. No external model call is made. Rule output is labelled 「规则生成」 / "Rule-based" (`app.rules`). Never write "AI reviewed" or similar.
- The old PR-model code goes. Its history stays in git (tag `legacy/pr-model`). No compatibility shims.
- Until Task 12 the whole repo does not typecheck, because the server and desktop still use the old model. Each task verifies its own package with the commands it gives.

## Review Focus

1. **A private item leaks to another person.** A private need, input, artifact, work item, chat or dashboard created by A must never reach B. The leak paths to check are B's event stream, B's SQLite cache, blob reads, a `need.shared` snapshot that carries other private data, and B's DOM. Tests: Task 1 (chat), Task 7 (service: privacy filter, snapshot fill, blob access), Task 7 `sync.e2e`, Task 12 e2e.
2. **Old-model data meets v3 code.** Two cases: a client with a v2-era cache, and a server pointed at an old schema. The server must refuse to start and name the unknown event type and the seq. It must not crash halfway through and must not write. The client reports skipped events and does not hide them. Tests: Task 7 ("opening a log with an unknown event type fails and names the type"), Task 11 (safeReplay reports skipped events).
3. **Sample data loaded twice, in the other language, or into a schema that already has data.** Each case is a no-op that reports `loaded: false`. There are never duplicate projects and never half-loaded data. Tests: Task 9.
4. **Two blocks running at once, or a busy port.** The isolation helper refuses to start on a busy port and names it. `reset` drops only `meetless_v3_(s|u1|u2|u3)` and refuses everything else, including `meetless`, `meetless_trial` and `meetless_trial_v3`. Tests: Task 12 (`blocks.test.mjs`).
5. **Sign-in edge cases.** Covered: a trailing slash or a missing scheme in the server URL, an invite code with spaces or in lower case, and redeeming against a server that has no invite route yet. Each shows a reason and the URL that was tried; none silently fails. Tests: Task 6 (`redeemInvite` against a 404 stub, trimmed code).

### Task 1: Core: private chat threads with the project agent

Design §8.8: every person's conversation with the project agent is saved and only that person sees it. Core has no chat events yet.

**Files:**
- Modify: `packages/core/src/types.ts`, `events.ts`, `reducer.ts`, `scope.ts`, `queries.ts`
- Test: `packages/core/test/chat.test.ts`

**Interfaces:**
- Consumes: `AgentReply` (`packages/core/src/agent.ts`), `dashboardKey` (`types.ts`), `TestLog` / `atlas()` (`test/log.ts`).
- Produces:
  - `ChatMessage { id: Id; text: string; reply: AgentReply; at: IsoTime; seq: Seq }`
  - `ChatThread { userId: Id; scope: Id; messages: ChatMessage[]; clearedSeq: Seq }`. `scope` is `'home'` or a project id.
  - `State.chats: Record<string, ChatThread>`, keyed by `dashboardKey(userId, scope)`. `emptyState()` returns `chats: {}`.
  - Events: `'chat.asked': { messageId: Id; scope: Id; text: string; reply: AgentReply }` and `'chat.cleared': { scope: Id }`.
  - `eventScope` for both events: `{ projectId: scope === 'home' ? null : scope, privateTo: actorId }`.
  - `viewFor` keeps only the viewer's threads. `shareableView` returns `chats: {}`.
  - `chatMessages(s: State, userId: Id, scope: Id): ChatMessage[]` returns messages with `seq > clearedSeq`, oldest first.

### Task 2: Core: work linking, rule-filled fields, artifact sharing, conflict owner

Three gaps between core and the design and prototype. First, an unlinked or rule-linked work item can be linked or ignored (prototype Q2). Second, the drawer marks a round that rules filled in (`AiMark`, 「规则生成 改」). Third, private artifacts can be shared later (design §5, 「公开到项目」). The design also says a conflict is decided by the importer **or the owner** (§5), but core lets only the importer decide.

**Files:**
- Modify: `packages/core/src/types.ts`, `events.ts`, `reducer.ts`, `scope.ts`, `detect.ts`, `queries.ts`, `dashboard.ts`
- Test: `packages/core/test/work.test.ts` (new), `packages/core/test/inputs.test.ts`, `packages/core/test/privacy.test.ts`

**Interfaces:**
- Consumes: Task 1 `State` shape.
- Produces:
  - `WorkItem` gains `ignored: boolean` and `autoLinked: boolean`. The `work.recorded` payload gains `autoLinked?: boolean`, which is `INVALID_EVENT` without `needId`.
  - `'work.linked': { workId: Id; needId: Id; effect?: WorkEffect | null }` sets `needId`, sets `effect` when given, and sets `autoLinked = false` and `ignored = false`. Linking shared work to a private need is `PRIVATE_ITEM`. The scope is the work item's own (project, privateTo).
  - `'work.ignored': { workId: Id }` sets `ignored = true`. Doing it again is `ALREADY_DECIDED`.
  - `isProgress(w)` becomes `!w.capture && !w.ignored`. Dashboard cards (`sharedWork` in `dashboard.ts`) also drop ignored items.
  - `Need` gains `autoRound: boolean`. It is `true` only when `extract.accepted` has no `roundId` and the current round was filled in. `need.updated` with `roundId` sets it to `false`.
  - `'artifact.shared': { artifactId: Id; snapshot?: { artifact: Artifact } }` mirrors `input.shared`. Only the owner may share. Sharing is `PRIVATE_ITEM` while the artifact links a private need. The scope is `open(projectId)`.
  - `conflict.resolved` is allowed for `deciderId`, or for the target need's `ownerId` while the conflict's status is `'open'`. Anyone else gets `NOT_AUTHORISED`.
  - `matchNeed(text: string, needs: Need[]): { needId: Id; by: 'code' | 'keywords' } | null` in `detect.ts`. It tries `codesIn` first, then the existing `similarNeed` rule.
  - `nextRound(s: State, projectId: Id): Round | null` returns the first `planned` round with `n` greater than the current round's.
  - `roundFeedback(s: State, roundId: Id): Need[]` returns shared needs with `fromRoundId === roundId`, in `createdSeq` order. This is the deliveries feedback list.

### Task 3: Core: "To confirm", questions, agent intents, and the freeze

Design §5 and §6 put three things in 「待确认」: detected items (accept or ignore each), conflicts, and the questions the system cannot settle ("拿不准才进待确认问人"). The prototype shows two such questions: Q2, an unlinked commit, and Q3, a need that has stalled before the deadline. Design §7 also lists handoff and stale checks as actionable intents. After this task, event types and runtime exports are frozen by a test.

**Files:**
- Modify: `packages/core/src/queries.ts`, `dashboard.ts`, `agent.ts`, `index.ts`, `test/dashboard-agent.test.ts`; `packages/i18n/scripts/catalogue.py` and the regenerated `packages/i18n/resources/*.json`
- Test: `packages/core/test/confirm.test.ts`, `packages/core/test/contract.test.ts`

**Interfaces:**
- Consumes: Task 2 `isProgress`, `nextRound`.
- Produces:
  - `type Question = { kind: 'unlinked'; projectId: Id; workId: Id } | { kind: 'stale'; projectId: Id; needId: Id; idleDays: number; daysLeft: number }`
  - `questionId(q: Question): string` returns `'unlinked:<workId>'` or `'stale:<needId>'`.
  - `STALE_IDLE_DAYS = 10` and `STALE_DUE_DAYS = 7`.
  - `questions(s: State, userId: Id, projectId: Id | null, today: IsoDate): Question[]`, built from two rules:
    - **unlinked:** `needId === null`, `!ignored`, and `w.by === userId`.
    - **stale:** all of the following hold:
      - the need is shared and open, in the current round, with status in `{todo, untested, parked}`;
      - `(ownerId ?? createdBy) === userId`;
      - it has no handoff other than `declined` or `done`;
      - `idleDays` (days since the last progress date, or `source.date` if there is none) is at least `STALE_IDLE_DAYS`;
      - `0 <= daysLeft <= STALE_DUE_DAYS`.
  - `PendingExtract { projectId: Id; inputId: Id; extractId: Id }`
  - `pendingExtractsFor(s: State, userId: Id, projectId: Id | null): PendingExtract[]` returns extracts with `state === null` in inputs imported by `userId`. It leaves out conflict-flagged extracts of shared inputs, because those are conflicts.
  - `ToConfirm { conflicts: Conflict[]; proposals: Proposal[]; extracts: PendingExtract[]; questions: Question[]; count: number }`
  - `toConfirm(s: State, userId: Id, projectId: Id | null, today: IsoDate): ToConfirm` lists conflicts where the user is the decider or the owner of an open conflict's need, and all open proposals. This changes the signature: `today` is added, and `projectId` is required (`null` means all projects).
  - `projectBadges(s, userId, projectId, today)` returns `{ inputs, board, total }`. `board` is the handoffs sent to the user (`sent`) plus `toConfirm.count`. `total` equals `board`.
  - The `HomeItems.confirm[].kind` union becomes `'conflict' | 'proposal' | 'extract' | 'question'`. The id is the conflict id, the proposal id, `${inputId}:${extractId}` or `questionId(q)`.
  - `suggestions(view, userId, scope, today, opts)`. `today` is the new fourth parameter.
  - New `AgentAnswer` variants:
    - `{ intent: 'handoff'; projectId: Id; needId: Id | null; toId: Id | null; cites: Id[] }` (project scope only).
    - `{ intent: 'stale'; items: { projectId: Id; handoffId: Id; needId: Id; fetched: number; current: number; reminded: boolean }[]; cites: Id[] }`.
    - The `'today'` item kind adds `'confirm'`, which covers extracts and questions.
  - Intent order in `answer()`: addCard, asInput, handoff, stale, delivery, weekly, today, deadlines, retrieval, summary.
    - `HANDOFF = /交给|转给|hand(?:\s+(?:it|this))?\s+(?:off|over)\s+to|assign\s+to/i`. The need comes from `codesIn` + `needByCode`. The member is the one whose `displayName` occurs in the text, case-insensitive.
    - `STALE = /过时|旧版本|stale|out of date|outdated/i`.
  - New i18n keys, in both languages: `ask.q.unlinked`, `ask.q.stale`, `ans.handoff`, `ans.handoffNone`, `ans.stale`, `ans.staleNone`, `ans.today.confirm`.
