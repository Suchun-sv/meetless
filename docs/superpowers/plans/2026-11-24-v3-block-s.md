# Meetless v3 Phase 1 Block S (Server, MCP, Accounts) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build every route in `@meetless/api` on the server: invite-code accounts with personal tokens, agent tokens and the agent call log, the need context endpoint that records fetches, import upload with server-side extraction, artifact reads, and the OnlyOffice config with its file ticket. Also serve MCP over HTTP from the server (`POST /mcp`, contract §12.1), rate-limit sign-in and invite redemption (§12.8), and write the Meetless skill, all tested against real Postgres, with an MCP end-to-end test.

**Architecture:** The server keeps its Phase 0 event channel. Accounts (invites, tokens, agent calls) live in new Postgres tables (migration 4). They are not events, because they hold secrets and machine state, not project records. Every new route is declared through one typed frame. The frame takes the method, path and auth from `API_ROUTES`, resolves a `Principal` from the bearer token, records agent-token calls on MCP routes, and maps errors to `ApiErrorBody`. Every read goes through `service.view(userId)`. Every write goes through `service.submit` (client-allowed types) or `service.appendTrusted` (service-only types and `via`). MCP is a thin adapter inside the server at `POST /mcp` (Streamable HTTP, stateless). It runs each tool through the handler of its `MCP_TOOL_ROUTE` route, with the same principal, call log and privacy filtering.

**Tech Stack:** Fastify 5 + ws, PostgreSQL 16 (`meetless-pg`, 55433), TypeScript 7 strict, vitest 5, `@modelcontextprotocol/sdk` 1.x + `zod`, `mammoth` (docx text), `unpdf` (pdf text), node:crypto (hashes, HMAC, HS256 JWT).

**Spec:** `docs/superpowers/specs/2026-11-24-meetless-v3-design.md` (binding; §8.3, §8.4, §8.5, §8.7, §10). Names: `docs/superpowers/plans/2026-11-24-v3-contract.md` (§3, §5, §9, §11, §12). ## Review Focus

1. **One invite redeemed twice at once** (two clients, or a double click). Expected: exactly one account, and the other request gets `INVITE_USED`. Test: Task 3 `two concurrent redeems create exactly one user`, plus Task 1's store race test.
2. **An agent token used as a full session.** An agent token pasted into the app, or used against `/v1/events`, `/v1/commands`, blobs or the websocket. Expected: refused. An agent token reaches only `auth: 'agent'` routes. Test: Task 2 `an agent token is refused on commands, events, blobs, ws and user API routes`.
3. **An import whose text cannot be read.** Scanned PDF, corrupt docx, a txt in GBK, or a retry after a timeout. Expected: `EXTRACT_FAILED` naming the reason and nothing appended. A retry with the same `inputId` returns the first result. Tests: Task 5 `an extraction failure answers EXTRACT_FAILED…`, `retrying the same inputId…`.
4. **Probing another person's private need through MCP.** For example, the code `Hp1` or a guessed artifact id. Expected: byte-for-byte the same `NOT_FOUND` as a missing code, so existence does not leak. Tests: Task 6 `another user's private need answers the same NOT_FOUND as a missing code`, Task 8 `another user's private artifact answers NOT_FOUND`.
5. **A ticket URL reused after it expired, or edited.** Also a ticket used after a server restart. Expected: `NOT_AUTHORISED`, with no file bytes. Test: Task 8 `an expired, tampered or other-server ticket is NOT_AUTHORISED`.

## DocumentServer reachability (S's ruling; U3 builds the container side)

**The problem.** Docker on the dev machine is rootless. Its config is `rootlesskit --net=gvisor-tap-vsock --disable-host-loopback`, read from the running process. So no container can open a connection to the host's 127.0.0.1, and the server must stay bound to 127.0.0.1. Changing the daemon would affect every other container on the machine, so that is ruled out.

**The mechanism: a Unix socket plus a relay container.**
- The server opens a second listener, which serves only `GET /v1/office-files/:ticket`. It is an HTTP server on a Unix socket at `MEETLESS_OFFICE_FILES_SOCKET`. The default is `<dataDir>/office-sock/files.sock`, and `off` disables it.
  - The socket file has mode `0600`, and its directory holds nothing else.
  - The TCP listener does **not** serve `/v1/office-files`.
- U3 runs the relay container `meetless-onlyoffice-files` on `meetless-dev-net`:
  - It uses image `meetless-office:dev`, which already has python3, so nothing is pulled.
  - It runs as `user: "0:0"`. Under rootless Docker, container root is the host user that runs Docker, which is the only user that can open a `0600` socket.
  - It bind-mounts the socket directory read-only at `/run/meetless`.
  - It runs a TCP-to-Unix byte relay (a script in `infra/dev/onlyoffice/`) that listens on `0.0.0.0:8080` inside the network. No port is published.
- DocumentServer fetches `${MEETLESS_PUBLIC_URL}/v1/office-files/<ticket>`. The default `MEETLESS_PUBLIC_URL` is `http://meetless-onlyoffice-files:8080`.
  - The relay resolves to a private address. DocumentServer must therefore run with `ALLOW_PRIVATE_IP_ADDRESS=true`, plus `JWT_ENABLED=true` and `JWT_SECRET` from `.env.local`.
- **Rejected alternatives.**
  - Binding the server to the LAN or Tailscale address breaks the 127.0.0.1 rule.
  - Host networking does not help, because under rootless Docker it is still the rootlesskit namespace.
  - Injecting an nginx include into the DocumentServer image depends on DocumentServer internals.
  - Copying files into a shared static directory duplicates blobs and moves the expiry check out of the server.
- **Mac trial.** Only the renderer moves to the Mac: it reaches `http://127.0.0.1:55435` through the SSH tunnel. The fetch path stays entirely on the dev server, so nothing changes.

### Task 11: Rate limits on sign-in and invite redemption

Contract §12.8. The code `RATE_LIMITED` is already in `API_ERROR_CODES`, and `error.RATE_LIMITED` is in the catalogue (base).

**Files:**

- Test: `apps/server/test/ratelimit.test.ts`

**Interfaces:**
- Consumes: Task 2 `Authenticator` and frame, Task 3 redeem, Task 9 `/mcp`; `ServerConfig.now`.
- Produces:
  - `class RateLimiter { constructor(opts: { limit: number; windowMs: number; now: () => Date }) }` with two methods:
    - `hit(key: string): void` counts one event.
    - `retryAfter(key: string): number | null`: null while fewer than `limit` events fall in the last `windowMs`, else the seconds until the oldest one leaves the window (rounded up, at least 1).
  - `SIGN_IN_LIMIT = { limit: 10, windowMs: 5 * 60_000 }` (10 failed sign-ins per 5 minutes) and `REDEEM_LIMIT = { limit: 10, windowMs: 10 * 60_000 }` (10 failed redemptions per 10 minutes). One limiter of each per server instance, so each `withServer` starts empty.
  - The key is the client IP (Fastify `request.ip`). The trust-proxy setup for the public deployment is a Phase 2 item.
  - Sign-in:
    - Only failures are counted and limited. A valid token always passes, even from a limited IP, so a shared NAT never locks everyone out. A request with no `Authorization` header does not count.
    - A failed check (`UNAUTHENTICATED` or `TOKEN_REVOKED`) on HTTP routes, `/mcp` or the websocket upgrade first asks `SIGN_IN_LIMIT.retryAfter(ip)`. When it is not null (10 failures already in the window), that failing request answers 429 `RATE_LIMITED` instead of 401 (the upgrade answers 429 before upgrading). Then it calls `hit(ip)`.
  - `invites.redeem`: a failed redemption (`INVITE_INVALID`, `INVITE_USED`) first asks `REDEEM_LIMIT.retryAfter(ip)`; when it is not null, that failing request answers 429 instead of its own code. Then it calls `hit(ip)`. A successful redemption always passes.
  - Every 429 body is `{ error: { code: 'RATE_LIMITED', details: { retryAfter } } }`.
